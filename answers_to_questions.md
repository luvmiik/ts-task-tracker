## В01. Сможет ли interface Student запретить серверу прислать {"id":"ошибка"}? Обсудите, где живёт интерфейс и где появляются данные.   

Ответ: Нет, не сможет. Интерфейс interface Student существует только на этапе компиляции (статической проверки типов) и полностью стирается при сборке в исполняемый JavaScript-код. Данные от сервера или из файла появляются уже во время выполнения программы (в рантайме). Поэтому важно разделять два действия: проверить программу (это делает компилятор TypeScript до запуска на основе типов) и проверить значение (это должна делать явно написанная функция валидации в выполняемом коде при получении внешних данных).   

## В02. Почему Student | { points: number } не гарантирует наличие одновременно name и points? Как изменится требование при использовании &?   

Ответ: Оператор | (объединение, union) допускает значение, которое соответствует либо типу Student, либо типу { points: number }. Поэтому у объекта гарантированно будут только те свойства, которые являются общими для обоих вариантов.   
При использовании оператора & (пересечение, intersection) тип потребует выполнить оба ограничения одновременно. Такой объект обязан иметь и все поля Student (включая name), и поле points.

## В03. Чем различаются типы mixed и pair? Как получить имя из pair и вызвать у него toUpperCase()? Почему такой же доступ к mixed[1] требует дополнительных проверок?   

```typescript 
const mixed = [1, 'Анна'];
const pair: [number, string] = [1, 'Анна'];
```

Ответ:Переменная mixed без явной аннотации выводится компилятором как массив произвольной длины (number | string)[], где на любой позиции может оказаться как число, так и строка. Переменная pair имеет тип кортежа [number, string], который жёстко фиксирует количество элементов и тип каждой позиции: по индексу 0 — строго number, по индексу 1 — строго string.   Для pair достаточно обратиться по индексу: pair[1].toUpperCase(), так как TypeScript точно знает, что на второй позиции находится строка. При обращении к mixed[1] возвращается тип string | number | undefined. У числа и undefined нет метода toUpperCase(), поэтому компилятор потребует предварительно сузить тип. 

## В04. Сформулируйте одной фразой, какую ошибку предотвращает unknown. 

Ответ: Тип unknown предотвращает обращение к свойствам и вызов методов у непроверенных значений до того, как разработчик явно докажет их тип в коде. 

## В05. Вызовите findById([{ name: "Анна" }], 1). Какое ограничение нарушено?   

Ответ: Нарушено ограничение обобщённого типа (generic constraint) T extends { id: number }. Переданный в массиве объект { name: "Анна" } не содержит обязательного числового поля id, которое требуется функции для сравнения элементов.

## В06. Почему нельзя прочитать result.value до проверки result.ok?   

Ответ: Потому что Result<T> представляет собой размеченное объединение (discriminated union): { ok: true; value: T } | { ok: false; error: string }. До проверки дискриминатора result.ok компилятор не знает, с каким из двух вариантов работает код. Во втором варианте ({ ok: false; error: string }) свойства value не существует, поэтому обращение к нему небезопасно и блокируется до сужения типа через if (result.ok).

## В07. Почему функция parseName принимает unknown, но в успешном варианте возвращает string? В какой строке возникает это основание?   

Ответ: Функция принимает unknown, так как на входе может оказаться любое непроверенное значение. Основание считать значение строкой возникает в строке с проверкой if (typeof value !== 'string') return .... Поскольку при любом другом типе происходит ранний выход из функции (return), во всех последующих строках срабатывает автоматическое сужение типа (type narrowing), и компилятор гарантированно знает, что value имеет тип string.

## В08. Перед вызовом addStudent предскажите результат для имён " Анна ", "" и числа 42 при группе "ЭГ-2". Почему после ошибки создание студента не продолжается?   

Ответ:" Анна " — вернёт { ok: true, value: { id: 1, name: 'Анна', group: 'ЭГ-2' } }.   
"" — вернёт { ok: false, error: 'Имя не должно быть пустым' }.   
42 — вернёт { ok: false, error: 'Имя должно быть строкой' }.   
Создание студента не продолжается благодаря конструкции раннего возврата if (!parsed.ok) return parsed;. Если parseName вернул ошибку, управление немедленно выходит из addStudent, не доходя до увеличения nextId++ и добавления записи в массив students.push(...).

## В09. Объясните, почему результат parseName с ошибкой подходит для возврата из addStudent, хотя успешные значения у функций имеют разные типы.   

Ответ: parseName возвращает Result<string>, а addStudent возвращает Result<Student>. После проверки if (!parsed.ok) тип переменной parsed сужается ровно до неуспешной ветки объединения: { ok: false; error: string }. Эта ветка не зависит от параметра типа T и структурно полностью идентична неуспешной ветке типа Result<Student>, поэтому компилятор позволяет вернуть её напрямую.

## В10. Где данные проверяются при выполнении, где типы проверяются до запуска и почему карточка (getStudentCard) действительно не содержит лишних полей?   

Ответ: До запуска: Компилятор tsc проверяет соответствие типов аргументов при вызовах функций, структуру интерфейсов (Student), полноту веток Result<T> и обработку возможного undefined.   
При выполнении: Выполняются проверки typeof value !== 'string', .trim(), проверка длины строки length === 0 и совпадение item.id === id.   
Почему карточка не содержит лишних полей: Сам по себе тип Pick<Student, 'id' 'name' |> существует только при компиляции и не удаляет свойства из объекта в памяти. Лишних полей (group, email) в карточке нет потому, что в теле функции getStudentCard мы явно конструируем новый объект { id: student.id, name: student.name }, копируя в него только два нужных свойства. 

## В11. Почему успешный npm run dev не заменяет npm run typecheck?   

Ответ: Команда npm run dev использует утилиту tsx, которая просто удаляет аннотации типов и быстро запускает код в Node.js без полноценной проверки совместимости типов. Только запуск npm run typecheck (tsc --noEmit) выполняет полную статическую проверку всего проекта по правилам tsconfig.json.

## В12. Почему const student = { name: "Анна" } позволяет изменить student.name?   

Ответ: Ключевое слово const защищает от переназначения саму переменную (ссылку на объект в памяти), но не делает неизменяемым содержимое объекта, на который она указывает.

## В13. Что произойдёт при поиске отсутствующего элемента и как это отражается в сигнатуре?   

Ответ: Метод массива .find() в JavaScript возвращает undefined, если ни один элемент не подошёл под условие. В сигнатуре функции это явно отражается через объединение с undefined: findById(...): T | undefined. Это обязывает вызывающий код проверить результат перед обращением к полям найденного объекта.

## В14. Какой информации о значении не хватает, если его тип unknown?   

Ответ: Не хватает абсолютно любой информации о структуре и типе значения: неизвестно, является ли оно примитивом, объектом, функцией, null или undefined. 

## В15. Как Result<T> связывает проверку ok с доступными полями?   

Ответ: Через общее литеральное поле-дискриминатор ok (true или false) в объединении типов (discriminated union). Когда мы пишем условие if (result.ok), компилятор сужает тип переменной до { ok: true; value: T } и открывает доступ к result.value. В ветке else (или после if (!result.ok)) тип сужается до { ok: false; error: string }, где доступно только поле result.error.  

## В16. Чем отличается Pick<Student, "id" "name" |> от создания объекта с двумя полями?   

Ответ: Pick<Student, "id" "name" |> — это утилитарный тип, который работает только во время компиляции: он создаёт новое описание типа на основе существующего интерфейса и стирается при сборке. Создание нового объекта { id: s.id, name: s.name } — это операция времени выполнения, которая физически выделяет память под новый объект в JavaScript без лишних свойств (group, email).
